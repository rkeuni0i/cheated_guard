# SpendGuard — 소비패턴 학습 기반 개인 카드 이상거래 탐지

> 개인의 평소 소비 분포를 통계적으로 학습하고, 그 분포에서 벗어난 결제를 실시간으로 포착해
> **알림 · 추가인증 · 카드정지**로 대응하는 하이브리드 FDS(Fraud Detection System)의 참조 구현.
>
> [`docs/PRD.html`](docs/PRD.html)(SpendGuard PRD v1.0)를 **자족형(self-contained)** 으로 구현했다.
> PostgreSQL·Redis·FastAPI·Kafka 없이 **Python + SQLite + 인메모리**만으로 데이터 생성부터
> 3계층 탐지·백테스트·대시보드까지 전 과정을 한 번에 실행·검증할 수 있다.

## 1. 왜 만들었는가

카드사는 이미 FDS를 운영한다. 그러나 그 기준은 **"카드사 전체 고객의 사기 패턴"** 에 맞춰져
있다. 해외 IP, 심야 고액 승인, 동일 가맹점 연속 승인 같은 *사기꾼의 행동*을 잡는 데 특화되어
있어, 두 구간이 비게 된다.

- **개인 기준으로는 이상한데, 전체 기준으로는 흔한** 결제 → 통과된다.
- **전체 기준으로는 이상한데, 그 사람에겐 평범한** 결제 → 오탐이 된다.

즉 이 프로젝트의 본질은 "사기 탐지"가 아니라 **"개인 소비 분포로부터의 이탈 탐지
(personal anomaly detection)"** 다. 사람마다 "평소"의 기준이 다르다는 사실을 정면으로 다룬다.

이를 실제로 구현하려면 세 가지 난제를 풀어야 했고, 그것이 이 저장소의 설계 전체를 지배한다.

| 난제 | 왜 어려운가 | 해결 |
|---|---|---|
| **"평소"의 정의** | 소비는 정규분포가 아니라 롱테일. 평균±3σ는 거의 모든 고액을 이상으로 만든다 | 로그변환 + MAD(로버스트 통계) — [ADR-002](docs/adr/002-robust-statistics.md) |
| **맥락 의존성** | 같은 30만원도 단골 가전매장이면 정상, 새벽 신규몰이면 이상 | 30개 상대값 피처(F01~F30) + 카테고리/가맹점 조건부 분포 |
| **오탐 비용의 비대칭** | 미탐은 금전 손실, 오탐은 계산대 앞에서 카드가 막히는 경험 | 등급별 액션 분리(R3=알림 / R4=정지) + 알림 피로도 관리 |

## 2. 사용자·사회적 이점

- **금융 취약계층 보호**: 보이스피싱·명의도용은 종종 "그 사람에게만" 이상한 결제로 나타난다.
  전사 FDS가 놓치는 이 구간을 개인 프로파일이 메운다. 특히 고령·자영업 사용자(PRD 페르소나
  P3)가 "조금이라도 이상하면 막아줘"라는 니즈를 민감도 프리셋으로 충족한다.
- **오탐 피로 없는 신뢰**: 대부분의 이상 후보는 사실 본인의 결제다. 그래서 자동정지는 최고위험
  (R4)에서만 하고, 나머지는 "알림 + 1탭 응답"으로 처리한다. 사용자가 기능을 꺼버리지 않게 하는
  것이 탐지율만큼 중요하다.
- **설명받을 권리**: 모든 판정에 *사람이 읽을 수 있는 근거*를 3줄 이내로 제공한다.
  "이상 거래입니다"(정보량 0)가 아니라 "전자·컴퓨터에서 평소 최고액의 3.5배이고, 처음 이용하는
  가맹점이에요". 자동화된 결정에 대한 이의제기·설명요구권(PRD 11.3)의 기술적 토대.
- **프라이버시 최소 수집**: 카드번호(PAN)·CVC·정확한 GPS·품목상세·주민번호를 **수집하지
  않는다**. 카드는 토큰으로만 참조하고, 지역은 시·군·구까지만. "덜 모으는 것"을 설계 원칙으로 둔다.

## 3. 무엇을 해결하는가 — 핵심 주장

| 구간 | 예시 | 기존 전사 FDS | SpendGuard |
|---|---|---|---|
| 개인 이상 · 전체 정상 | 월 60만원 쓰는 사람의 30만원 PC부품 단건 | 통과 (금액·업종 흔함) | **개인 분포 상위 → 이상 후보** |
| 전체 이상 · 개인 정상 | 매달 올리브영 20만원 쓰는 사람의 동일 결제 | 고액 뷰티로 오탐 가능 | **프로파일 일치 → 통과** |

이 두 줄을 동시에 만족시키는 것이 이 시스템의 존재 이유다.

## 4. 기술 스택과 선택 근거

이 저장소는 **자족형 구현**이다. "실시간 이상탐지"라는 말에 이끌려 Kafka·Spark를 먼저
도입하는 흔한 실수를 피했다 — 요구는 *"거래 1건당 3초 이내"* 이지 *"초당 10만 건"* 이 아니다.
단건 저지연과 대용량 처리량은 전혀 다른 문제다([ADR-001](docs/adr/001-no-kafka.md)).

| 영역 | 사용 기술 | 왜 | 프로덕션 대응(PRD) |
|---|---|---|---|
| 언어 | **Python 3.9+** | 데이터·통계·ML 생태계 일원화 | Python 3.12 |
| 통계·수치 | **NumPy** | 분위수·MAD·로그정규 계산 | 동일 |
| ML | **scikit-learn** (IsolationForest) | 라벨이 거의 없어 비지도 우선 | + LightGBM 승격 |
| 저장 | **SQLite** (표준 라이브러리) | 멱등 인덱스·append-only·재현성 의미 보존 | PostgreSQL 16 |
| 캐시·벨로시티 | **인메모리 sliding window** | Redis ZSET과 동일 의미(조회 후 기록) | Redis 7 |
| 데이터 검증 | **dataclass** | 스키마 명시 | Pydantic + FastAPI |
| 대시보드 | **정적 HTML 생성** | 외부 의존 없이 시각 리포트 | Streamlit / Next.js |
| 테스트 | **pytest** | unit·property·integration | + testcontainers |

의존성은 `numpy`, `scikit-learn`, `pandas` 세 개뿐. 나머지는 표준 라이브러리다.

## 5. 아키텍처

```
                     외부(카드사 API/시뮬레이터/CSV)
                              │ raw tx
        ┌─────────────────────▼─────────────────────┐
        │ ① 수집: 검증(DQ) → 정규화 → 멱등 dedup      │
        └─────────────────────┬─────────────────────┘
                    ┌──────────┴──────────┐
        ┌───────────▼──────────┐  ┌───────▼────────────────────────────┐
        │ ④ Profiling Path      │  │ ③ Scoring Path (실시간, 동기)       │
        │  (배치): 90일 로버스트 │  │  피처(F01~F30) → L1│L2│L3          │
        │  통계 → user_profiles │─▶│  → 융합 → 등급(R0~R4) → 근거        │
        └───────────────────────┘  └───────┬────────────────────────────┘
                                   ┌────────▼────────────────────────────┐
                                   │ ⑤ 액션: 알림 / 추가인증 / 카드정지    │
                                   │ ⑥ 피드백: 사용자 응답 → 라벨 → 개선   │
                                   └──────────────────────────────────────┘
```

**3계층 하이브리드** — 세 계층은 서로 다른 실패 모드를 가지므로, 조합했을 때 견고해진다.

| 계층 | 방식 | 강점 / 약점 | 파일 |
|---|---|---|---|
| **L1 룰** | 15개 결정론적 룰, 수확 체감 합산 | 즉시 설명가능 / 새 패턴 미대응 | `detection/rules.py` |
| **L2 통계** | 4개 축(금액·맥락·시간·벨로시티), 로버스트 | 사용자별 자동 적응 / 상호작용 못 봄 | `detection/statistics.py` |
| **L3 ML** | IsolationForest(비지도), 선택적 | 조합 패턴 포착 / 블랙박스 | `detection/ml.py` |

융합(`detection/fusion.py`)은 가중결합 → 최대계층 가산 → 맥락보정 → HARD OVERRIDE
(화이트리스트·여행모드·억제·강제심각) 순. **L3가 죽어도 L1+L2로 판정이 계속된다**(내결함성).

## 6. 구현 워크플로우 (M1→M4)

PRD 로드맵을 그대로 따라, "L1+L2로 핵심을 먼저 증명하고 ML은 나중에"라는 순서를 지켰다.

| 단계 | 산출물 | 파일 |
|---|---|---|
| **M1 · 데이터 기반** | 합성 생성기(부록A), 수집·정규화, DQ-01~08, 14종 택소노미, 특수가맹점 분류 | `simulator/`, `ingestion/`, `taxonomy.py` |
| **M2 · 프로파일·룰** | F01~F30 피처(단일구현+누수방지), 로버스트 프로파일, peer 콜드스타트, L1 15룰, L2 4축, 근거 생성 | `features/`, `profiling/`, `detection/rules.py`, `statistics.py`, `explain.py` |
| **M3 · ML·액션** | IsolationForest, 스코어 융합, 등급판정, 카드 상태머신, 피드백 루프 | `detection/ml.py`, `fusion.py`, `engine.py`, `actions/` |
| **M4 · 완성도** | walk-forward 백테스트, 성능지표, PSI 드리프트, HTML 대시보드, 테스트 | `ops/`, `scripts/`, `tests/` |

각 판정은 **재현 가능**하다 — 프로파일·룰·모델 버전과 피처 스냅샷을 판정 결과에 함께 기록한다
(PRD NFR-07, `test_reproducibility`로 검증).

## 7. 문제 발현과 해결 — 실제 디버깅 여정

구현이 끝나고 백테스트를 처음 돌렸을 때 **Recall@FPR가 34%** 였다(목표 85%). 여기서부터가
진짜 작업이었다. 아래는 실제로 겪은 문제와 해결 과정이다.

### 문제 ① 프로파일 오염 — 정상 사용자가 너무 "부자"로 보였다
- **발현**: 어떤 사용자의 `p99 = 12,980,000원`. 그 결과 40만원 사기가 "정상 범위"로 통과.
- **원인**: 생성기에서 프리랜서 아키타입의 `variance_multiplier(2.2) × HIGH 카테고리 σ(1.4)
  = 3.08`. 로그정규에 σ 3은 수백만~천만원대 이상치를 자연 발생시킨다.
- **해결**: σ를 1.2로 상한, 금액을 150만원으로 캡. 정상 프로파일이 현실적으로 좁아지자
  사기가 비로소 이상으로 떠올랐다. → PR-AUC 0.35 → 0.47.

### 문제 ② 탐지 불가능한 라벨이 recall을 눌렀다
- **발현**: 이상(positive)의 45%가 SC-05(소액 유출)인데, 30,000원 결제는 개별적으로는 절대
  구별 불가.
- **해결**: SC-05를 "점증형(4만→35만원)"으로 재설계. 초반은 못 잡아도 후반은 잡히는, 누적
  탐지에 부합하는 현실적 시나리오로 바꿨다.

### 문제 ③ 여행 중 해외결제가 임계값을 오염시켰다
- **발현**: SC-10(여행 해외결제) 87건이 R2 근처에 몰려 진짜 이상과 경쟁 → precision 저하.
- **원인**: PRD가 설계한 **여행 모드** 완화 장치를 백테스트가 사용하지 않았다.
- **해결**: 생성기가 SC-10 주입 시 여행 기간을 함께 등록하고, 융합에서 여행모드+해외면
  점수를 상한 처리. → Precision@top0.5% 62% → 78%.

### 문제 ④ hard negative가 "신규 가맹점"으로 보였다
- **발현**: SC-08(월급날 정기 보험료 45만원)이 R3로 과탐.
- **원인**: 일회성으로 주입돼 시스템 입장에선 처음 보는 가맹점.
- **해결**: hard negative에 **사전 이력**(12개월치 정기 보험료 등)을 심어 "익숙한 맥락"을
  실제로 만들어줬다. 그래야 단골 감쇠·routine 감쇠가 작동한다. → 하드네거티브가 정상 등급으로.

### 문제 ⑤ 스케일 회귀 — 40명에선 잘 되는데 200명에선 무너졌다
- **발현**: PR-AUC가 40명 0.60 → 200명 0.35로 급락. 특정 사용자의 보험료 거래가 **5,246건**,
  결제 간격 중앙값이 3일(월 1회여야 정상).
- **원인**: hard negative 개수를 `전체 거래 수 × 2%`로 잡았다. 그런데 각 사건이 최대 14개
  거래(사전 이력 포함)를 만들어내서, 거래 수가 커질수록 같은 사용자에게 수백 건이 몰려
  프로파일을 오염시켰다. routine 탐지도 이 때문에 실패했다(간격이 불규칙해짐).
- **해결**: 사건 수를 **거래 수가 아니라 사용자 수에 비례**시켰다(사용자당 이상 ~3건,
  hard negative ~2건). 스케일에 무관하게 밀도가 일정해지고 오염이 사라졌다.
  → 200명 Event Recall 69% → 79%, Precision 50% → 57%.

### 문제 ⑥ "건 단위 recall"은 다건 사기에 맞지 않는 지표였다
- **통찰**: 카드도난 연속결제(SC-02)의 *첫 1~2건*은 개별적으로 정상과 구별 불가. 그래서 건
  단위 recall은 구조적으로 낮을 수밖에 없다. 하지만 운영에서 중요한 건 **사건을 카드정지
  이전에 잡는 것**이다.
- **해결**: **사건 단위 Recall(Event Recall)** 을 추가했다. 사건 내 한 건이라도 R3+면 탐지로
  간주(그 시점에 카드가 정지되어 후속 결제 차단). FDS 평가의 표준 관점. 진단 출력으로 확인:
  ```
  SC-02: 396,985원 → R2 (아직 속도 신호 미형성)
         410,208원 → R2
         474,051원 → R3 ← 이 시점에 카드 정지, 이후 결제 차단
  ```

### 그 밖의 소소한 것들
- `tx_sum_24h` 피처 누락으로 L2 벨로시티 축이 KeyError → 피처 딕셔너리에 추가.
- 금액대 버킷(억제 규칙 키)을 융합과 피드백이 공유해야 해서 `fusion_bands.py`로 분리.

**교훈**: 이 프로젝트에서 탐지 성능의 대부분은 모델이 아니라 **데이터 생성 가정의 현실성**과
**평가 지표의 적합성**에서 나왔다. 합성 데이터로 검증할 때 가장 위험한 함정이 바로 이것이다.

## 8. 결과

합성 데이터 기준, walk-forward 백테스트(미래 정보 누수 차단). 규모에 따라:

| 지표 | 40명×9개월 | 200명×12개월 | 목표 |
|---|---|---|---|
| **Event Recall (R3+)** | **79.3%** | **79.3%** | — |
| Recall @ FPR 0.5% (건 단위) | 68.6% | 42.9% | ≥85%* |
| Precision @ top 0.5% | **77.4%** | 57.4% | ≥60% |
| **Lift @ 1%** | **60.8×** | **45.2×** | ≥20× |
| PR-AUC | 0.636 | 0.393 | — |

등급 분포는 R0 59% / R1 29% / R2 8% / R3 2.1% / R4 0.2%로 **PRD 7.1의 기대 발생률과 일치**한다.

\* 건 단위 Recall@FPR가 목표에 못 미치는 것은 [문제 ⑥](#7-문제-발현과-해결--실제-디버깅-여정)에서
설명한 대로 다건 사기의 초기 셋업 거래가 개별 탐지 불가능하기 때문이며, **설계상 정상**이다.
운영상 의미 있는 지표는 사건 단위 Recall(79%)이다.

시각 리포트: `python scripts/run_pipeline.py` 실행 후 `data/report.html`.

## 9. 설계 판단 (ADR)

이 프로젝트의 값어치는 "ML을 썼다"가 아니라 **판단의 근거**에 있다.

- **[ADR-001] Kafka 미도입** — 저지연 단건 요구를 대용량 처리량 문제로 오해하지 않는다.
- **[ADR-002] 평균±3σ 대신 median·MAD·분위수** — 롱테일 분포에서 평균 기반은 스스로 무력화된다.
- **[ADR-003] R4 자동정지에 L1 룰 히트 필수** — 설명 불가능한 이유로 카드를 막지 않는다.
  ML은 판단을 강화할 뿐 단독 근거가 되지 않는다. (대표 시나리오가 R4가 아닌 R3인 이유)
- **무응답을 정상으로 라벨링하지 않는다**(`actions/feedback.py`) — 학습 데이터 오염 방지.
- **누수 방지**(`features/`) — 모든 참조는 현재 거래를 제외한 과거 정보만. 벨로시티는 조회 후 기록.

## 11. 한계와 정직한 고지

- **합성 데이터 기준**이다. 생성기가 만든 분포로 학습하고 같은 생성기가 만든 이상을 탐지하면
  성능이 좋게 나오는 것이 당연하다. 이를 "모델이 잘한다"고 주장하면 안 된다. 생성 가정은
  `simulator/generator.py`(PRD 부록 A)에 전부 명시했다. 실서비스 전환 시 공개 데이터셋
  (IEEE-CIS Fraud Detection 등)으로 같은 파이프라인을 교차검증해야 한다.
- **법적 전제**: 타인의 금융거래 정보를 상시 수집·분석하는 서비스는 신용정보법상 마이데이터
  허가 또는 카드사 제휴가 필요하다. 본 프로젝트는 합성 데이터 또는 사용자 본인이 업로드한 자기
  데이터만 사용하며, 실서비스 전환 시 법률 검토를 전제로 한다.
- **ML의 겸손한 위치**: L3(ML)의 성능 기여는 생각보다 작고 구현 비용은 크다. L1+L2가 핵심
  주장을 증명하며, ML은 선택적 강화 계층이다(`--no-ml`로 끄고 비교 가능). 계층별 기여를 정직하게
  보고하는 것이 오히려 분석 역량의 증거다.
