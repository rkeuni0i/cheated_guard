00문서 개요

이 문서는 “사용자 결제 데이터를 축적해 평소 소비 범위를 학습하고, 그 범위를 벗어난 거래를 이상으로 판정해 알림·카드정지로 이어지게 한다”는 초기 워크플로우를 실제로 구현 가능한 수준까지 구체화한 것이다. 기획서(PRD)와 기술 지침서를 하나로 합쳤으며, 각 장은 다음 독자를 대상으로 한다.

01프로젝트 정의

1.1 배경과 문제 정의

카드사는 이미 FDS를 운영하지만, 그 기준은 “카드사 전체 고객의 사기 패턴”에 맞춰져 있다. 해외 IP, 심야 고액 승인, 동일 가맹점 연속 승인 같은 사기꾼의 행동 패턴을 잡는 데 특화되어 있어서, 다음 두 구간이 비게 된다.

구간사례기존 FDSSpendGuard
개인 기준 이상 · 전체 기준 정상평소 월 60만 원 쓰는 사용자의 30만 원 PC 부품 단건 결제정상 통과 (금액·가맹점 모두 흔함)개인 분포 상위 0.3% → 이상 후보
전체 기준 이상 · 개인 기준 정상매달 올리브영에서 20만 원씩 쓰는 사용자의 동일 패턴 결제고액 뷰티 결제로 오탐 가능개인 프로파일과 일치 → 통과

즉 이 프로젝트의 본질은 “사기 탐지”가 아니라 “개인 소비 분포로부터의 이탈 탐지(personal anomaly detection)”이다. 이 구분이 프로젝트 전체의 설계 판단을 지배한다. 라벨(사기 여부)이 거의 없다는 뜻이고, 따라서 6장의 모델 설계는 지도학습이 아니라 비지도 + 룰 + 약한 라벨 조합을 중심에 둔다.

해결해야 할 3가지 핵심 난제

  1. “평소”의 정의 — 소비는 정규분포가 아니다. 대부분 소액이고 가끔 고액인 롱테일·로그정규 형태다. 단순 평균±3σ는 거의 모든 고액 결제를 이상으로 만든다. → 6.3에서 로버스트 통계로 해결.
  2. 맥락 의존성 — 같은 30만 원도 “매달 가던 가전 매장”이면 정상, “처음 보는 온라인 부품몰 + 새벽 3시”면 이상이다. 금액 하나로 판단할 수 없다. → 5장 피처 설계로 해결.
  3. 오탐 비용의 비대칭 — 미탐 1건은 금전 손실이지만, 오탐 1건은 계산대 앞에서 카드가 막히는 경험이다. 사용자는 오탐 3회면 기능을 꺼버린다. → 7장 등급별 액션 분리로 해결.

  • 카드사 전사 사기 패턴 탐지 — 도난·복제·가맹점 공모 등 크로스 유저 패턴은 다루지 않는다. 오직 개인 프로파일 이탈만 본다.
  • 신용평가·한도 산정 — 신용정보법상 별도 인가 영역이며 목적 외 이용에 해당한다.
  • 실시간 스트리밍 인프라(Kafka/Flink) 구축 — 포트폴리오 규모에서는 과잉이다. 3.4에서 대체안을 제시한다.
  • 다국가·다통화 지원 — KRW 단일 통화, 국내 가맹점만 가정한다(해외 거래는 룰 R-07로 일괄 고위험 처리).

설계 판단 — 왜 R3에서 자동 정지를 하지 않는가

원안은 “이상 추정 → 알림, 카드 정지”를 한 묶음으로 봤다. 그러나 이 시나리오는 사용자 본인이 실제로 PC 부품을 산 경우가 훨씬 흔하다. 정지를 즉시 실행하면 결제가 끊기고, 사용자는 매장에서 당황한다. 따라서 정지는 R4에서만 자동으로 하고, R3는 “알림 + 사용자가 아니라고 답하면 즉시 정지”로 분리한다. R4의 조건은 7.1에 정의한다.

3.3 이중 경로 데이터 플로우

A. Profiling Path — “평소”를 만드는 경로 (비동기/배치)

  1. 윈도우 선택 — 최근 90일. 90일 미만이면 보유 전체를 쓰되 콜드스타트 플래그를 세운다(5.4).
  2. 전처리 — 취소된 거래 제외, 할부는 원금액 기준 1건으로 통합, routine_flag=true 거래는 별도 집합으로 분리.
  3. 집계 — 전체·카테고리별·시간대별 3층에 대해 n, median, MAD, p75, p90, p95, p99, max, 로그평균, 로그표준편차 산출.
  4. 행동 프로파일 — 신규 가맹점 비율, 심야(00~06시) 거래 비율, 온라인 비율, 시간대 히스토그램(24bin), 요일 히스토그램(7bin), 주간 거래 건수 EWMA.
  5. 저장 — user_profiles에 새 버전으로 append. 덮어쓰지 않는다(과거 판정 재현용).
  6. 캐시 워밍 — 활성 사용자 프로파일을 Redis에 profile:{user_id}로 적재, TTL 26시간.

B. Scoring Path — “이상”을 잡는 경로 (동기/실시간)

  1. 수신·정규화 — 멱등키 (card_id, approval_no, approved_at)로 중복 차단.
  2. 실시간 피처 — Redis 슬라이딩 윈도우에서 1시간/24시간 거래 건수·합계를 O(1)로 조회.
  3. 프로파일 로드 — 캐시 히트 시 <1ms, 미스 시 DB 조회 후 캐시 채움.
  4. 3계층 병렬 실행 — L1/L2는 인프로세스(합계 <10ms), L3는 별도 프로세스 호출(예산 300ms).
  5. 융합·등급 — 6.5 공식 적용.
  6. 액션·기록 — 액션 실행은 비동기 큐에 넣고 판정 응답은 즉시 반환한다.

카드 원번호(PAN), CVC, 유효기간, 정확한 GPS 좌표, 구매 품목 상세, 주민등록번호는 수집하지 않는다. 카드는 반드시 발급사가 제공한 토큰 또는 자체 해시(SHA-256(PAN + per-user salt))로만 참조한다. 지역은 시·군·구 단위로 절삭한다. 이 결정은 11.2의 데이터 최소화 원칙과 직결되며, 포트폴리오 문서에서도 심사자가 가장 먼저 확인하는 지점이다.

수집 방식 3가지

  1. 시뮬레이터(기본) — 부록 A의 생성기로 사용자 200명 × 12개월 합성 거래 약 25만 건 생성. 이상 시나리오를 라벨과 함께 주입하므로 성능 측정이 가능하다.
  2. 마이데이터 표준 API 형식 모사 — 카드 업권 “승인내역 조회” 응답 스키마를 참고해 필드명을 맞춰 두면, 실제 연동 시 어댑터 교체만으로 동작한다.
  3. CSV 업로드 — 사용자가 카드사 홈페이지에서 내려받은 이용내역을 직접 업로드. 데모에 유용하다.

# 가맹점을 특수(high-variance)로 자동 분류
# 전체 사용자 거래를 대상으로 주 1회 실행

def classify_merchant_variance(merchant_txs):
    """
    변동계수(CV)와 사분위범위비(QCD)를 함께 본다.
    CV만 쓰면 극단값 한 건에 흔들리므로 로버스트 지표를 병행.
    """
    amounts = merchant_txs.amount
    if len(amounts) < 30:
        return "MID"                      # 표본 부족 → 중립

    cv  = amounts.std() / amounts.mean()
    q1, q3 = amounts.quantile([0.25, 0.75])
    qcd = (q3 - q1) / (q3 + q1)           # 0~1, 로버스트

    if cv >= 1.0 or qcd >= 0.45:
        return "HIGH"    # 올리브영·다이소형 : 3천원도 30만원도 정상
    if cv <= 0.35 and qcd <= 0.20:
        return "LOW"     # 지하철·구독형 : 금액이 거의 고정
    return "MID"


# routine_flag 판정 : 주기성 + 금액 안정성
def is_routine(user_merchant_txs):
    if len(user_merchant_txs) < 3:
        return False
    intervals = user_merchant_txs.approved_at.diff().dt.days.dropna()
    period_stable = intervals.std() <= 5 and 25 <= intervals.median() <= 35
    amount_stable = (user_merchant_txs.amount.std()
                     / user_merchant_txs.amount.mean()) <= 0.15
    return period_stable and amount_stable
왜 “올리브영”이 까다로운가

같은 가맹점에서 3,000원(립밤)부터 300,000원(화장품 세트)까지 나온다. 전체 금액 분포로 보면 30만 원은 상위 0.2%지만, 올리브영이라는 조건 하에서는 상위 8%일 수 있다. 그래서 is_special=true 가맹점은 전체 분포가 아니라 P(amount | merchant, user)를 쓰고, 개인 이력이 부족하면 P(amount | merchant)(전체 사용자 기준)로 폴백한다. 이 폴백 체인이 6.3의 3단 구조다.

def normalize_merchant(raw: str) -> str:
    s = raw.strip().lower()

# ── Redis 슬라이딩 윈도우 : 벨로시티 피처 ──────────────────────
# ZSET key: velo:{user_id}  member: tx_id  score: unix_ts

async def record_and_get_velocity(r, user_id: str, tx_id: str,
                                   amount: int, ts: float) -> dict:
    k_cnt = f"velo:{user_id}"
    k_amt = f"veloamt:{user_id}"
    k_mch = f"velomch:{user_id}"

    pipe = r.pipeline()
    # 1) 만료 데이터 제거 (24시간 초과)
    pipe.zremrangebyscore(k_cnt, 0, ts - 86400)
    pipe.zremrangebyscore(k_amt, 0, ts - 86400)
    pipe.zremrangebyscore(k_mch, 0, ts - 86400)
    # 2) 조회 (현재 거래 기록 이전에!)
    pipe.zcount(k_cnt, ts - 3600,  ts)      # tx_count_1h
    pipe.zcount(k_cnt, ts - 86400, ts)      # tx_count_24h
    pipe.zrangebyscore(k_amt, ts - 3600,  ts)
    pipe.zrangebyscore(k_amt, ts - 86400, ts)
    pipe.zrangebyscore(k_mch, ts - 3600,  ts)
    res = await pipe.execute()

    cnt_1h, cnt_24h = res[3], res[4]
    sum_1h  = sum(int(m.split(':')[1]) for m in res[5])
    sum_24h = sum(int(m.split(':')[1]) for m in res[6])
    distinct_mch_1h = len({m.split(':')[1] for m in res[7]})

    # 3) 현재 거래 기록 (조회 이후 — 누수 방지)
    pipe = r.pipeline()
    pipe.zadd(k_cnt, {tx_id: ts})
    pipe.zadd(k_amt, {f"{tx_id}:{amount}": ts})
    pipe.zadd(k_mch, {f"{tx_id}:{merchant_id}": ts})
    pipe.expire(k_cnt, 90000); pipe.expire(k_amt, 90000); pipe.expire(k_mch, 90000)
    await pipe.execute()

    return {"tx_count_1h": cnt_1h, "tx_count_24h": cnt_24h,
            "tx_sum_1h": sum_1h,  "tx_sum_24h": sum_24h,
            "distinct_merchants_1h": distinct_mch_1h}

-- ── 프로파일 배치 : PostgreSQL 한 방 쿼리로 전체 통계 산출 ─────
WITH base AS (
    SELECT user_id, amount, category, merchant_id, approved_at,
           ln(amount) AS log_amt
    FROM   transactions
    WHERE  approved_at >= now() - INTERVAL '90 days'
      AND  tx_type = 'APPROVAL'
      AND  is_excluded = FALSE
),
overall AS (
    SELECT user_id,
           count(*)                                              AS n,
           sum(amount)                                           AS total,
           percentile_cont(0.50) WITHIN GROUP (ORDER BY amount)  AS median,
           percentile_cont(0.75) WITHIN GROUP (ORDER BY amount)  AS p75,
           percentile_cont(0.90) WITHIN GROUP (ORDER BY amount)  AS p90,
           percentile_cont(0.95) WITHIN GROUP (ORDER BY amount)  AS p95,
           percentile_cont(0.99) WITHIN GROUP (ORDER BY amount)  AS p99,
           max(amount)                                           AS max_amt,
           avg(log_amt)                                          AS log_mean,
           stddev_samp(log_amt)                                  AS log_std
    FROM base GROUP BY user_id
),
-- MAD(중앙값 절대편차)는 2-pass 필요
mad_calc AS (
    SELECT b.user_id,
           percentile_cont(0.50) WITHIN GROUP (ORDER BY abs(b.amount - o.median)) AS mad,
           percentile_cont(0.50) WITHIN GROUP (ORDER BY abs(b.log_amt - ln(o.median))) AS mad_log
    FROM base b JOIN overall o USING (user_id)
    GROUP BY b.user_id
),
by_cat AS (
    SELECT user_id, category,
           count(*) AS n,
           percentile_cont(0.50) WITHIN GROUP (ORDER BY amount) AS median,
           percentile_cont(0.95) WITHIN GROUP (ORDER BY amount) AS p95,
           max(amount) AS max_amt,
           sum(amount)::numeric / sum(sum(amount)) OVER (PARTITION BY user_id) AS share
    FROM base GROUP BY user_id, category
)
SELECT o.*, m.mad, m.mad_log,
       jsonb_object_agg(c.category,
           jsonb_build_object('n', c.n, 'median', c.median, 'p95', c.p95,
                              'max', c.max_amt, 'share', round(c.share,4),
                              'fallback', c.n < 5)) AS cat_stats
FROM overall o
JOIN mad_calc m USING (user_id)
JOIN by_cat  c USING (user_id)
GROUP BY o.user_id, o.n, o.total, o.median, o.p75, o.p90, o.p95, o.p99,
         o.max_amt, o.log_mean, o.log_std, m.mad, m.mad_log;

5.3 온라인·오프라인 피처 일관성

학습 시(배치, pandas)와 판정 시(실시간, Python 함수)가 다른 코드로 같은 피처를 계산하면 반드시 어긋난다(training-serving skew). 이를 막는 세 가지 장치:

  1. 단일 구현 원칙 — 피처 계산 함수는 features/transforms.py 한 곳에만 둔다. 배치는 이 함수를 df.apply로 감싸 호출하고, 실시간도 같은 함수를 dict에 대해 호출한다.
  2. 피처 스냅샷 저장 — 판정 시 사용한 피처값을 risk_assessments.features(JSONB)에 그대로 저장한다. 재학습 시 이 스냅샷을 학습 데이터로 쓰면 skew가 원천 차단된다.
  3. 일관성 테스트 — CI에서 동일 거래 100건에 대해 배치 경로와 실시간 경로 피처를 비교, 상대오차 1e-6 초과 시 빌드 실패(13.1 AC-FEAT-01).

def get_reference_stats(user_profile, category):
    """3단 폴백 체인"""
    cat = user_profile.cat_stats.get(category)
    if cat and cat["n"] >= 5:
        return cat, "PERSONAL"                       # ① 개인 카테고리 통계
    if user_profile.tx_count >= 30:

                     peer_stats(user_profile.peer_id, category),

    return peer_stats(user_profile.peer_id, category), "PEER"   # ③ peer만

6.1 3계층 하이브리드 설계

단일 모델로 가지 않는 이유는 명확하다. 룰만 쓰면 새로운 패턴을 못 잡고, ML만 쓰면 왜 막혔는지 설명할 수 없으며 규제 대응이 불가능하다. 세 계층은 서로 다른 실패 모드를 가지므로 조합했을 때 견고해진다.

L1 · 룰 엔진 결정론적 · <5ms · 100% 설명가능

명시적 임계 조건. “개인 p99 초과”, “신규 가맹점 20만 원 이상”처럼 사람이 읽고 검증할 수 있다. 강점: 즉시 배포·즉시 이해·오작동 시 즉시 차단. 약점: 조건 조합 폭발, 새 패턴 미대응.

L2 · 통계 모델 적응형 · <5ms · 수식으로 설명가능

개인 분포에서의 이탈 정도를 연속값으로 산출. 로버스트 통계(MAD, 분위수)를 쓰므로 극단값에 흔들리지 않는다. 강점: 사용자마다 자동으로 기준이 달라짐. 약점: 피처 간 상호작용을 못 본다(금액은 정상인데 시간+가맹점 조합이 이상한 경우).

L3 · ML 모델 비선형 · ~300ms · SHAP로 설명

다변량 상호작용을 학습. 1단계는 IsolationForest(비지도, 라벨 불필요), 라벨이 500건 이상 쌓이면 2단계 LightGBM(지도)로 승격. 강점: 조합 패턴 포착. 약점: 블랙박스성, 드리프트 취약, 학습 데이터 필요.

def score_l1(hits: list[Rule]) -> tuple[int, list[dict]]:
    """
    단순 합산이 아니라 '수확 체감(diminishing returns)'을 적용한다.
    룰 5개가 동시에 히트해도 점수가 200이 되면 안 되고,
    서로 상관된 룰(R-01과 R-02는 거의 같이 히트)의 중복 가산을 막아야 한다.
    """
    if not hits:
        return 0, []

    # 가중치 내림차순 정렬 후 기하급수 감쇠
    ws = sorted((h.weight for h in hits), reverse=True)
    raw = sum(w * (0.6 ** i) for i, w in enumerate(ws))
    #   1등 100%, 2등 60%, 3등 36%, 4등 21.6% ...

    score = min(100, round(raw * 100 / 45))   # 45점 ≈ 만점 기준 정규화
    reasons = [{"code": h.id, "label": h.render_message(),
                "contribution": round(h.weight * (0.6 ** i) / raw, 3)}
               for i, h in enumerate(sorted(hits, key=lambda x: -x.weight))]
    return score, reasons

6.3 L2 통계 모델

왜 평균±3σ를 쓰면 안 되는가 — 이 프로젝트의 핵심 통계 판단

개인 결제 금액은 강한 우편향(right-skewed) 롱테일 분포다. median 18,400원인 사용자의 평균은 26,000원, 표준편차는 45,000원쯤 나온다. 평균+3σ = 161,000원이므로 그 이하는 전부 정상으로 통과된다. 게다가 과거에 한 번 있었던 고액 결제가 표준편차를 부풀려 임계값을 스스로 무력화한다. 해결책은 두 가지를 동시에 쓰는 것이다: ① 로그 변환으로 분포를 대칭에 가깝게 만들고, ② MAD(중앙값 절대편차)로 극단값 영향을 제거한다.

L2를 구성하는 4개 축

# ── 축 1. 로그-로버스트 Z (전체 분포 이탈도) ────────────────────
# MAD에 1.4826을 곱하면 정규분포에서 표준편차와 동일한 스케일이 된다.

def axis_amount(amount, profile):
    log_amt    = math.log(amount)
    log_median = math.log(profile["median"])
    scale      = 1.4826 * profile["mad_log"]
    scale      = max(scale, 0.35)          # 하한: 지출이 지나치게 균일한 사용자 보호
    z = (log_amt - log_median) / scale
    # z를 0~100으로 사상 : z=2 → 40점, z=3 → 60점, z=5 → 87점
    return 100 * (1 - math.exp(-max(z - 1.0, 0) / 2.2))


# ── 축 2. 조건부 분위수 (카테고리/가맹점 맥락) ───────────────────
def axis_context(amount, profile, category, merchant):
    ref, source = get_reference_stats(profile, category)   # 5.4 폴백 체인

    if merchant.is_special:
        # 특수 가맹점: 전체가 아니라 '이 가맹점에서의 내 분포'로 판단
        ref = profile.merchant_stats.get(merchant.id) or ref

    # 경험적 분위수 → 상위 꼬리만 점수화
    q = empirical_percentile(amount, ref)      # 0~1
    if q < 0.95:
        return 0
    score = (q - 0.95) / 0.05 * 100            # 0.95→0, 1.0→100
    # peer 기반이면 신뢰도가 낮으므로 감쇠
    return score * (1.0 if source == "PERSONAL" else 0.7)


# ── 축 3. 시간 이례도 ──────────────────────────────────────────
def axis_time(hour, dow, profile):
    hh = profile["time_stats"]["hour_hist"]
    p_hour = hh[hour]
    # 라플라스 스무딩으로 0확률 방지
    p_smooth = (p_hour * profile["n"] + 1) / (profile["n"] + 24)
    surprise = -math.log(p_smooth)             # 정보량(bit)
    baseline = -math.log(1 / 24)               # 균등분포 기준 3.18
    return min(100, max(0, (surprise - baseline) / baseline * 100))


# ── 축 4. 벨로시티 이탈 ────────────────────────────────────────
def axis_velocity(feats, profile):
    daily_avg = profile["monthly_sum_ewma"] / 30
    ratio_sum = feats["tx_sum_24h"] / max(daily_avg, 10000)
    weekly_avg_cnt = profile["weekly_tx_count_ewma"] / 7
    ratio_cnt = feats["tx_count_24h"] / max(weekly_avg_cnt, 1)
    r = max(ratio_sum, ratio_cnt)
    if r <= 2.0:
        return 0
    return min(100, (r - 2.0) / 6.0 * 100)     # r=8 → 100점


# ── 융합 ──────────────────────────────────────────────────────
L2_WEIGHTS = {"amount": 0.40, "context": 0.30, "time": 0.12, "velocity": 0.18}

def score_l2(tx, profile, feats):
    axes = {
        "amount":   axis_amount(tx.amount, profile),
        "context":  axis_context(tx.amount, profile, tx.category, tx.merchant),
        "time":     axis_time(tx.hour, tx.dow, profile),
        "velocity": axis_velocity(feats, profile),
    }
    # routine 거래는 전체 감쇠 (원안의 '단순 거래 제외')
    damp = 0.3 if tx.routine_flag else 1.0
    # 단, routine이어도 평소의 3배를 넘으면 감쇠 해제
    if tx.routine_flag and feats["amt_over_median"] >= 3.0:
        damp = 1.0

    score = sum(L2_WEIGHTS[k] * v for k, v in axes.items()) * damp
    return round(min(100, score)), axes

def train_stage1(df_normal):

        n_estimators=300,

def score_l3(tx_features, model, qt, calib):
    X = qt.transform([[tx_features[f] for f in L3_FEATURES]])
    raw = -model.score_samples(X)[0]        # 클수록 이상
    # 원점수는 스케일이 없으므로 학습셋 분포 기준 분위수로 캘리브레이션
    pct = calib.percentile_of(raw)          # 0~1
    return round(pct * 100)

① 시간 순 분할. 랜덤 K-fold를 쓰면 미래 거래로 과거를 예측하는 셈이 되어 성능이 부풀려진다.
② 라벨의 편향 인식. 사용자 응답 라벨은 알림을 보낸 거래에만 존재한다. 알림을 안 보낸 거래는 라벨이 없지 정상이 아니다. 이를 무시하고 “무알림=정상”으로 학습하면 모델이 현재 룰을 그대로 복제하게 된다(selection bias). 해결책: 매일 소량(0.5%)을 무작위로 알림 보내 편향 없는 라벨을 확보하거나, PU-learning 기법을 적용한다.
③ ML 점수 단독으로 카드를 정지하지 않는다. R4 자동 정지는 항상 L1 룰 히트를 필수 조건으로 둔다(7.1). 설명할 수 없는 이유로 카드를 막으면 안 된다.

BASE_WEIGHTS = {"l1": 0.35, "l2": 0.35, "l3": 0.30}

def fuse(l1, l2, l3, l3_status, tx, profile, feats):
    # 1) L3 실패 시 가중치 재정규화
    if l3_status != "OK":
        w = {"l1": 0.54, "l2": 0.46, "l3": 0.0}
        l3 = 0
    else:
        w = BASE_WEIGHTS

    base = w["l1"]*l1 + w["l2"]*l2 + w["l3"]*l3

    # 2) 최대 계층 가산 — 한 계층만 강하게 반응한 경우를 놓치지 않는다
    strongest = max(l1, l2, l3)
    score = 0.75 * base + 0.25 * strongest

    # 3) 맥락 보정 (가감산, 각 항목 상한 존재)
    adj = 0
    if feats["mtd_over_monthly_ewma"] < 1.0:      adj -= 3   # 이번달 지출 정상
    if feats["is_installment"]:                    adj -= 5   # 할부 = 계획된 소비
    if profile["is_cold_start"]:                   adj -= 8   # 근거 부족 → 보수적
    if feats["merchant_tx_count"] >= 10:           adj -= 12  # 단골 가맹점
    if feats["is_overseas"]:                       adj += 10
    if feats["tx_count_1h"] >= 5:                  adj += 8
    adj = max(-20, min(20, adj))

    score = max(0, min(100, round(score + adj)))

    # 4) HARD OVERRIDE — 스코어와 무관하게 결과를 강제
    if tx.merchant_id in user_whitelist(tx.user_id):
        return 0, "WHITELIST"
    if travel_mode_active(tx.user_id) and feats["is_overseas"]:
        return min(score, 45), "TRAVEL_MODE"       # R2 이하로 제한
    if feats["rule_hit_R09"]:                      # 소액테스트→고액 패턴
        return max(score, 92), "FORCED_CRITICAL"   # 무조건 R4

    return score, "NORMAL"

0.35/0.35/0.30은 임의값이 아니라 시작점이다. 다음 절차로 조정한다.

  2. 목적함수는 FPR ≤ 0.5% 제약 하의 Recall 최대화.
  3. 상위 5개 조합의 성능 차이가 2%p 이내면 가장 L1 비중이 높은 조합을 택한다(설명가능성 우선).

6.7 임계값 튜닝 방법론

“몇 점부터 이상인가”는 통계 문제가 아니라 비용 문제다. 다음 비용 함수를 최소화하는 임계값을 찾는다.

Cost(θ) = C_FN · FN(θ) + C_FP · FP(θ) + C_FRICTION · StepUp(θ)

  C_FN       = 미탐 1건 비용     ≈ 평균 피해액 × 미복구율
  C_FP       = 오탐 1건 비용     ≈ 사용자 불편 + 이탈 확률 × LTV
  C_FRICTION = 추가인증 1건 비용 ≈ C_FP × 0.15

포트폴리오 환경에서는 실제 금액을 알 수 없으므로 상대비 C_FN : C_FP = 10 : 1을 기본 가정으로 두고, 민감도 프리셋에 따라 5:1(보수) ~ 20:1(민감)으로 변경한다. 이 가정을 문서에 명시하는 것 자체가 설계 성숙도의 지표다.

단계작업산출물

def to_grade(score, l1_reasons, profile) -> str:
    base = ("R4" if score >= 90 else "R3" if score >= 70 else
            "R2" if score >= 50 else "R1" if score >= 30 else "R0")

    # 강등 : R4 자격 미달
    if base == "R4":
        has_high_rule = any(r["severity"] == "HIGH" for r in l1_reasons)
        if not has_high_rule or profile.is_cold_start:
            base = "R3"

    # 강등 : 알림 피로도 상한 (7.3)
    if base in ("R2", "R3") and alerts_today(profile.user_id) >= DAILY_CAP:
        if base == "R2":
            base = "R1"                      # R2는 억제
        # R3 이상은 상한과 무관하게 발송 — 안전이 우선

    # 승격 : 사용자 민감도 프리셋
    if profile.sensitivity == "HIGH":
        base = bump_up(base, steps=1, max_grade="R3")   # R4 승격은 금지
    elif profile.sensitivity == "LOW":
        base = bump_down(base, steps=1)

    return base

문구 작성 원칙

  • 사실 → 근거 → 행동 순서. 무엇이 일어났는지 먼저 말하고, 왜 알리는지 설명하고, 무엇을 하면 되는지 제시한다.

  • 숫자를 반드시 넣는다. 사용자가 기억을 대조할 수 있어야 한다.
  • 공포 마케팅 금지. “해킹 위험!” 같은 표현은 신뢰를 깎는다.
  • R4는 이미 조치했음을 먼저 알린다. “정지할까요?”가 아니라 “정지했어요”.

무응답의 원인은 다양하다 — 알림을 못 봤을 수도, 폰을 잃어버렸을 수도, 실제로 카드를 도난당해 대응 중일 수도 있다. 이를 “정상”으로 라벨링하면 모델이 진짜 사기 케이스를 정상으로 학습하는 최악의 오염이 발생한다. 무응답은 라벨 없음(unlabeled)으로 두고, PU-learning이나 준지도 학습에서만 활용한다.

  • 버저닝 — URL 경로에 /v1. 파괴적 변경 시에만 버전 상승, 최소 6개월 병행 운영.

10.3 드리프트 모니터링

# PSI (Population Stability Index) — 피처 분포 변화 감지
# 학습 시점 분포(expected) vs 최근 7일 분포(actual)

def psi(expected, actual, bins=10):
    breaks = np.percentile(expected, np.linspace(0, 100, bins + 1))
    breaks[0], breaks[-1] = -np.inf, np.inf
    e = np.histogram(expected, breaks)[0] / len(expected)
    a = np.histogram(actual,   breaks)[0] / len(actual)
    e, a = np.clip(e, 1e-6, None), np.clip(a, 1e-6, None)
    return float(np.sum((a - e) * np.log(a / e)))

# 판정 기준
#   PSI < 0.10  안정          → 조치 없음
#   0.10~0.25   경미한 변화    → 주간 리포트에 기록, 관찰
#   PSI ≥ 0.25  유의한 변화    → 재학습 트리거 + 운영 알림 P1
감시 대상지표주기임계조치
입력 피처 분포PSI (피처별)일간≥ 0.25재학습 트리거
스코어 분포평균·p95 이동일간±20%임계값 재검토
등급 분포R3+ 비율일간기대치의 2배 초과즉시 조사 P0

10.4 챔피언-챌린저 운영

  • 섀도우 모드 — 챌린저는 실제 트래픽을 받아 판정하지만 액션을 실행하지 않는다. 챔피언과 결과를 나란히 기록해 2주간 비교한다.
  • 비교 기준 — 동일 거래에 대한 등급 불일치율, 챌린저 단독 탐지 건의 사후 라벨, 지연 시간.
  • 승격 조건 — 10.2 게이트 전부 통과 AND 챌린저 단독 탐지의 Precision ≥ 챔피언 수준 AND 지연 SLA 위반 없음.
  • 롤백 — 승격 후 72시간 내 R3+ 발생률이 이전 대비 2배를 넘으면 자동 롤백. 모델 버전은 즉시 전환 가능하도록 레지스트리에서 포인터만 변경한다.

타인의 금융거래 정보를 상시 수집·분석하는 서비스는 국내에서 신용정보법상 본인신용정보관리업(마이데이터) 허가 또는 카드사와의 정식 제휴가 필요하다. 개인이 만든 앱이 사용자 계정 정보를 받아 카드사 사이트를 대신 조회(스크래핑)하는 방식은 약관 위반이자 법적 위험이 크다. 본 프로젝트는 합성 데이터 또는 사용자가 직접 내려받아 업로드한 자기 데이터만을 사용하며, 실서비스 전환 시 반드시 법률 검토를 선행한다는 전제를 문서 전면에 명시한다. 이 문장을 넣는 것 자체가 포트폴리오 심사에서 감점이 아니라 가점 요소다.

11.3 자동화된 의사결정과 설명요구권

카드 정지는 사용자 권익에 실질적 영향을 주는 자동화된 결정이다. 따라서 다음을 보장한다.

  • 사전 고지 — 온보딩에서 “자동 정지가 발생할 수 있음”과 그 조건을 명시하고, 자동 정지 자체를 거부(opt-out)할 수 있게 한다.
  • 설명 제공 — 모든 정지에는 사람이 읽을 수 있는 근거 3개 이내를 함께 제공한다(6.8).
  • 이의 제기 경로 — 앱 내 1탭으로 해제 요청, 운영자 수동 검토 요청 가능.
  • 사람의 개입 — R4 정지는 24시간 내 운영자 사후 검토 큐에 자동 등록된다.

11.4 공정성·편향 점검

13.3 백테스트 프로토콜

# 백테스트는 반드시 "그 시점에 알 수 있었던 정보만" 사용해야 한다.
# Walk-forward 방식으로 시간을 따라가며 재현한다.

def backtest(users, start_date, end_date):
    results = []
    for day in daterange(start_date, end_date):
        # 1) 그날 새벽 프로파일 갱신 (그 이전 90일 데이터로만)
        profiles = {u: build_profile(u, window_end=day) for u in users}

        # 2) 그날 거래를 시간 순으로 판정
        for tx in transactions_on(day, order_by="approved_at"):
            feats = build_features(tx, profiles[tx.user_id],
                                   velocity_up_to(tx.approved_at))  # ← 미래 배제
            assessment = assess(tx, profiles[tx.user_id], feats)
            results.append({
                "tx_id": tx.id, "score": assessment.score,
                "grade": assessment.grade,
                "truth": injected_label(tx.id),      # 시뮬레이터가 아는 정답
            })
    return evaluate(results)   # PR-AUC, Recall@FPR, Precision@k, 세그먼트별

합성 데이터의 정직한 한계

생성기가 만든 분포로 학습하고 같은 생성기가 만든 이상을 탐지하면 성능이 좋게 나오는 것이 당연하다. 이를 “모델이 잘한다”고 주장하면 안 된다. 발표·문서에서는 반드시 “합성 데이터 기준 성능이며, 생성 가정은 부록 A에 명시했다”고 밝히고, 가능하면 공개 데이터셋(IEEE-CIS Fraud Detection, Kaggle Credit Card Fraud 등)에서 같은 파이프라인을 돌린 보조 결과를 함께 제시한다. 한계를 스스로 밝히는 것이 신뢰도를 가장 크게 올린다.
